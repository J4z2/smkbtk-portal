# Source, assets and prototype notes

## Source provenance

- Source: `SMK-Bandar-Tasik-Kesuma-Portal-Tingkatan-1-6-v12.html`.
- Located in the user's local `Desktop/sekolah` folder, associated with the SMK portal work.
- Original size: 241,864 bytes.
- Original SHA-256: `df3566905aa497524eacd6828a4183bc0c2f7186385537045232231bb0368a61`.
- Packaged: 29 September 2026.
- v12 was selected because the request specifically preferred that version. Later v13/v14 visual variants were not merged into this package.
- The original file was not modified. The project mirror's `sources/` directory was also left untouched.

The original single stylesheet was moved to `styles.css`; its single script was moved to `app.js`. `index.html` loads both through relative paths. Formatting and explanatory comments were added without changing application logic. Existing CSS cascade order, inline handlers, element IDs, data, copy and generated HTML strings are preserved.

## Assets and dependencies

No images, font files, CDN scripts, API endpoints or external stylesheets are required. There are no remote URLs in the original source. The crest and school illustration use CSS/text; charts and certificates use inline graphics/markup. The font stack names Inter followed by system fonts, but does not download an Inter font file. Exact font/emoji appearance may therefore vary by operating system.

Student photo uploads use FileReader data URLs and are saved inside browser data. They do not create files in an assets folder. If you later add assets, create an `assets/` directory and use relative paths such as `assets/school-logo.png` so direct opening still works.

- Parent: linked children, published academic reports, attendance details and absence requests, announcements, meetings, family profile, COEx progress and acknowledgement.
- Teacher: assigned students/classes/subjects, report edits and submissions, daily attendance, COEx checkpoint marks and student analytics.
- Super admin: report review/approval/publication, student/guardian records, photo upload, class moves/archive, CSV import, teacher access, school master data, audit, JSON export, COEx rules and intervention records.

## Existing limits retained from v12

1. **Frontend demo:** accounts and passwords are visible in JavaScript/browser storage. Role-specific screens simulate access; they are not a security boundary. There is no database or server API in this source.
2. **Demo content:** demo names, `@smkbtk.com` demo logins and seed dates (June 2026 attendance, session 2026/Penggal 1) are placeholders. School address, phone and email are blank until the super admin enters them in Data sekolah. Meeting slots are still fixed demo dates.
3. **Reset and migration:** `resetDemo()` restores the raw seed; reload afterwards to reapply `migratePortalData()` and restore all Tingkatan 1–6 classes, accounts and subject profiles. Migration also restores predefined records on later loads. Editing or deleting them only through the UI may not persist as expected.
4. **CSV import:** quoted fields (including commas inside quotes) are supported. Columns are `name,id,classId,guardian,phone` and optional `gender`. Use existing class IDs; a header such as `Nama,ID,Kelas,Penjaga,Telefon,Jantina` is recognised by the word `Nama`. Rows with duplicate or invalid student IDs (letters, numbers, - and _ only) or unknown class codes are skipped and listed after import. Newly created guardian entries do not automatically receive usable login credentials.
5. **Storage:** changes stay on the current browser; image data can exhaust browser storage. The original save routine catches storage failures and sets `window.__storageUnavailable`, so visible in-memory changes are not proof that they will survive a reload.
6. **PDF and print:** browser printing and the certificate preview remain available. Buttons that say a PDF will be generated by a future backend remain demonstration placeholders.
7. **JSON export:** downloads `smk-btk-data-YYYY-MM-DD.json`. There is no matching JSON restore workflow.

Any browser behaviour observed during packaging is recorded in VERIFICATION.md. This extraction does not silently apply the functional or visual changes from later redesigns.
